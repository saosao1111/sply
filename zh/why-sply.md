# 为什么是 SPLY

## 不是“发个币”，而是“把发射做成产品”

很多平台都能完成部署代币这一步，但真正难的是把下面这些步骤收成一个稳定产品：

- 谁负责部署 token
- 谁负责接收和保管募资
- 谁在 hard cap 达成后建立流动性
- 谁负责打开交易
- 谁负责清理临时权限
- 谁负责把源码送去验证
- 谁负责把项目和代币信息呈现在前台

SPLY 的价值在于，这些步骤不是散落在不同脚本里，而是被组织成同一条平台级流程。

## 为什么项目方会在乎这件事

如果平台只负责“发一个代币”，项目方最终还是要自己面对：

- 预售资金安全
- LP 初始化
- 权限收口
- 验证提交
- 页面展示

这会把一个本来应该标准化的产品，重新变回多个技术动作的临时拼接。SPLY 想解决的就是这个问题：把项目方从“组合脚本”的工作中解放出来。

## 为什么开发者会在乎这件事

开放模板是一把双刃剑。没有模板能力，平台扩展慢；模板能力完全放开，又会让平台标准崩掉。

SPLY 的思路是：

- 允许开发者提交模板
- 但模板不是独立生态
- 模板进入平台后，仍然受平台审核、注册、地址规划、验证链路和状态收口约束

这意味着开发者可以扩展机制，但不能把平台变成无序的模板市场。

## 为什么集成方会在乎这件事

钱包、机器人、终端和数据方最怕的是每个模板都需要重新理解一遍状态结构。SPLY 的目标是让集成方面对的是平台级的稳定结构，而不是每个项目的定制流程。

平台对外暴露的是：

- 稳定的工厂体系
- 稳定的项目索引
- 稳定的项目页与代币页 API
- 稳定的 finalize 后状态
- 稳定的模板审核与模板上线流程

## SPLY 的差异化优势

## 1. 模板与平台标准不是对立关系

SPLY 不是把模板能力做成平台规则的例外，而是把模板纳入平台规则本身。

## 2. 平台关心的是“发射完成后的标准状态”

发射不是在创建交易成功时结束，而是在 token 进入标准市场状态后才算真正闭环。

## 3. 平台把地址规划、验证和展示当成系统能力

地址确定性、自动验证、项目和代币展示，这些能力不是附属脚本，而是平台的一部分。

## 4. 平台允许更复杂的机制，但不放弃边界

SPLY 支持内置模板，也支持开发者模板，但前提是模板要服从平台边界，而不是直接控制平台资金与状态机。
